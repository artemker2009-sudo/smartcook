# CLAUDE.md — правила проекта SmartCook

## ⛔ Правила безопасности (обязательны ВСЕГДА)

Сверяйся с этим разделом перед **каждой** правкой бэкенда или базы данных.

### 1. RLS обязателен на каждой таблице с пользовательскими данными

У нас Supabase, и anon-ключ публично доступен в браузере — любой может делать запросы к API от имени анонимного клиента. Поэтому:

- **Каждая** таблица с пользовательскими данными обязана иметь включённый Row Level Security (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
- Каждая política обязана проверять владельца записи, например:

```sql
CREATE POLICY "users_select_own"
ON public.recipes
FOR SELECT
USING (auth.uid()::text = session_id);
```

- **Запрещено** писать `USING (true)` (или `WITH CHECK (true)`) без проверки владельца. Если данные действительно публичные для всех — это должно быть явное осознанное решение, зафиксированное комментарием в миграции, а не значение по умолчанию.
- Отдельные политики нужны для каждой операции: SELECT, INSERT, UPDATE, DELETE. Для INSERT/UPDATE обязателен `WITH CHECK` с проверкой владельца.
- Помни про типы колонок: если владелец хранится как text (session_id), сравнивай `auth.uid()::text = session_id`; если как uuid (user_id) — `auth.uid() = user_id` без каста.

### 2. Каждый эндпоинт проверяет владение данными

Любой новый эндпоинт (API-роут, edge function, RPC), который читает или пишет данные пользователя:

- Проверяет аутентификацию пользователя (реальный JWT для залогиненных).
- Гарантирует, что пользователь работает **только со своими записями** — фильтрация по владельцу из проверенной сессии, а не из параметров запроса.
- Никогда не доверяет user_id/session_id, переданному клиентом в body/query как единственному доказательству владения.
- Не отдаёт в ответе лишние поля (помним инцидент: /api/feed отдавал session_id всех рецептов — это фактически токен доступа).
- Пробрасывает Authorization-заголовок в Supabase-клиент (createRequestScopedClient), иначе RLS увидит anon и сломает легитимные сценарии залогиненных.

### 3. Новая таблица = RLS-политика в той же миграции

При создании любой новой таблицы:

- В **той же миграции** сразу: `ENABLE ROW LEVEL SECURITY` + все нужные политики.
- Миграция без RLS-политик для новой таблицы с пользовательскими данными считается неполной.
- Чек перед коммитом миграции: RLS включён? Политики покрывают SELECT/INSERT/UPDATE/DELETE? Нигде нет `USING (true)` без проверки владельца?

### 3.1. Перед правкой RLS — прочитать `pg_policies` по таблице ЦЕЛИКОМ

**SQL-файлы в репозитории не описывают то, что реально лежит в базе.** За одну сессию (19.09.2026) трижды подряд оказалось, что файл задаёт правильные политики, а рядом с ними в базе живёт старая широкая — и работает именно она.

- Перед любой правкой политик смотреть фактическое состояние:

```sql
select policyname, cmd, permissive, roles, qual, with_check
from pg_policies
where schemaname = 'public' and tablename = '<таблица>'
order by cmd, policyname;
```

- **Дропать политики перечислением из каталога, а не по именам.** Имя старой политики заранее неизвестно, и `drop policy if exists "<то, что ожидал файл>"` её не тронет — на этом споткнулись все три раза:

```sql
do $$
declare pol record;
begin
  for pol in select policyname from pg_policies
             where schemaname = 'public' and tablename = '<таблица>' and cmd = '<КОМАНДА>'
  loop
    execute format('drop policy %I on public.<таблица>', pol.policyname);
  end loop;
end $$;
```

- **Имена вида `Enable ... access for all users`, `Allow public ... on ...`, `public_all_*` — дефолт дашборда Supabase.** Это первое, что надо искать: они создаются кликом в UI, в репозитории их нет, и именно они пережили три чистки по имени.
- **Permissive-политики складываются по ИЛИ:** одна широкая обесценивает все строгие рядом. Restrictive — по И, поэтому для страховки нужна именно restrictive.
- **Restrictive для `{anon}` не защищает от залогиненного.** Роль `public` включает и `anon`, и `authenticated`; ограничитель, покрывающий только анона, оставляет дыру для любого, кто зарегистрируется. Ровно так рецепты можно было воровать через PATCH по id.
- **`as restrictive for all` использовать нельзя**, если нужно публичное чтение: restrictive распространится и на SELECT.
- RLS не умеет скрывать КОЛОНКУ. Если поле нельзя отдавать клиенту — это привилегия, а не политика: снять табличный `grant select` и выдать поколоночный. Табличный `GRANT` перекрывает поколоночный, поэтому сначала `revoke`, потом `grant (список)`.
- Новая `security definer` функция не видна PostgREST, пока не выполнен `notify pgrst, 'reload schema'` — до этого она отдаёт 404 PGRST202 всем ролям, включая service_role, и выглядит как «не создалась».

### 3.2. Результат правки RLS проверять РАНТАЙМОМ, а не текстом политики

- **Заблокированная запись выглядит как успешная.** `UPDATE`/`DELETE`, отбитые RLS, отдают 204 или 200 с пустым массивом — тот же ответ, что и при успехе. Всегда перечитывать значение обратно.
- **На пустой таблице закрытая и открытая политика неотличимы.** Для пробы создать строку через service_role и удалить её после.
- Проверять обе роли отдельно: анонимную и залогиненную. Дыра, из-за которой можно было присвоить чужой рецепт, была видна только под залогиненным.
- Тестовый запрос должен повторять то, что делает приложение. Проба с `Prefer: return=representation` без списка колонок бьёт по `RETURNING *` и даёт ложную «поломку прода», хотя код так не делает.

### 4. Секретные ключи — только на сервере

- `service_role`-ключ Supabase, ключи OpenAI и любые другие секреты хранятся **только** в переменных окружения на сервере.
- **Никогда** не попадают в клиентский код, бандл, публичные репозитории или логи.
- В браузер может попадать только публичный anon-ключ.
- `.env` и аналогичные файлы обязаны быть в `.gitignore`. Перед каждым коммитом проверять, что секретов нет в staged.

### 5. Валидация и санитизация пользовательского ввода

- Санитизировать текстовые поля перед вставкой в БД (обрезка длины, удаление управляющих символов).
- Ограничивать размер загружаемых фото и длину текстовых запросов до вызова OpenAI (защита от раздувания расходов).
- Помнить: OpenAI послушно вернёт любое название блюда — контент-фильтр это отдельная задача, не access control.

## Чек-лист перед любой правкой бэкенда / БД

- [ ] Новые/изменённые таблицы: RLS включён, политики с проверкой владельца написаны в той же миграции.
- [ ] Нет `USING (true)` / `WITH CHECK (true)` без осознанного обоснования.
- [ ] Эндпоинты берут владельца из проверенной сессии/JWT, а не из параметров клиента.
- [ ] Ответы API не содержат чужих записей и лишних полей (особенно session_id).
- [ ] Серверные компоненты/страницы (RSC), читающие таблицы с пользовательскими данными, выбирают ЯВНЫЙ список колонок, а не `select=*`: всё, что уходит пропом в клиентский компонент, попадает в SSR/RSC-пейлоад браузера. Пример: `/recipe/[id]` читает recipes без session_id/user_id.
- [ ] Секреты не попали в клиентский код, коммиты и логи.
- [ ] Перед правкой политик прочитан `pg_policies` по таблице целиком; дроп — перечислением из каталога, а не по именам (см. 3.1).
- [ ] Результат правки проверен рантаймом — чтением значения обратно, под анонимной И залогиненной ролью (см. 3.2).
- [ ] После миграции прогнан аудит-запрос из `supabase_recipe_likes_policy_fix.sql` (он же в `supabase_recipes_update_policy_fix.sql`, запрос 4). Он возвращает таблицы и команды, открытые кому угодно на запись. **Ожидаемый результат — только осознанно открытое:** `INSERT` в `analytics_events`, `parties`, `party_messages`. Всё новое в выдаче — разбирать до коммита миграции.
- [ ] Изменения под git, есть возможность отката. Для миграций, затирающих прежнее значение (например перенос владельца), прежнее значение сохранено в колонке — иначе откат невозможен в принципе.

## Проверки прода: не нагружать прокси

Весь трафик на smartcook.pro и smart-cook.pro идёт через наш nginx-прокси 193.124.128.87, а через него — все пользователи из РФ. Для Vercel это один IP. Серия запросов с него выглядит как атака: DDoS Mitigation вешает Challenge (403) на прокси, и сайт перестаёт открываться у всех, кто за ним. На Hobby system bypass недоступен. Случилось 22.09.2026: проверка favicon через curl и check-host дважды включила Challenge.

1. К smartcook.pro и smart-cook.pro — **не больше ОДНОГО запроса на адрес за проверку**. Никаких серий, циклов и повторов, никакого check-host и внешних сканеров без отдельного «ок» основателя.
2. Всё, что нужно проверить много раз (заголовки, кэш, замеры), проверять по прямому адресу деплоя `*.vercel.app`, минуя прокси. Эти адреса закрыты Vercel Authentication (без заголовка — 302 на вход), поэтому запросы шлются с заголовком `x-vercel-protection-bypass: $VERCEL_AUTOMATION_BYPASS_SECRET` (Protection Bypass for Automation, разрешён основателем 22.09.2026). Секрет лежит только в `.env.local`: не коммитить, не печатать в вывод и отчёты (никаких `curl -v`/`-i` с этим заголовком и `echo` переменной), не пересылать. Прод — `https://smartcook-artems-projects-f11c3a7b.vercel.app`, превью ветки — адрес из комментария Vercel в PR.
3. Если прод отдаёт 403 с `x-vercel-mitigated` — это защита Vercel сработала на прокси. Ничего не чинить, запросы не повторять, сразу сообщить основателю.

## Премиум (платная подписка)

Введён 24.09.2026. Задание целиком — `docs/premium/SPEC.md`, утверждённый макет
страницы — `docs/premium/premium-page.dc.html`, текст оферты — `docs/premium/oferta.md`.

### Флаг

`FEATURE_PREMIUM` в `lib/features.ts` — единственный флаг, который читается ИЗ
ОКРУЖЕНИЯ (`NEXT_PUBLIC_FEATURE_PREMIUM`), а не задан константой: включать
Премиум нужно сперва только на превью, а константа одинакова везде, куда доехал
коммит. Нет переменной → флаг false → в проде ничего не меняется.

**Что от флага НЕ зависит и работает всегда:** страницы `/premium` и `/oferta`
(их открывает и проверяет Robokassa) и запись в `podbor_usage` (данные копим с
первого дня, иначе включать лимит придётся вслепую).

### Таблицы (миграция `supabase_premium.sql`, прогнана 24.09.2026)

`premium_settings` (одна строка настроек), `podbor_usage` (журнал подборов),
`premium_orders` (заказы, **id = InvId для Robokassa**), `user_premium` (срок),
`premium_grants` (лог выдач админом).

У всех пяти RLS включён, **политик для anon/authenticated нет вообще**, плюс
явный `REVOKE` — как у `ai_rate_limit_events`. Читает и пишет только сервер под
service_role, с личностью из проверенного JWT (`getVerifiedUserId`). Здесь
лежат деньги и срок Премиума: любая политика для `authenticated` — это дверь,
через которую человек продлевает себе срок прямым REST-запросом с anon-ключом
из бандла.

### Что считается подбором

Подбор = человек даёт **новый ввод**, ИИ подбирает по нему рецепты.

| Роут | Считается | Почему |
|---|---|---|
| `/api/photo-recipe` (ветка с фото) | да, `photo` | новое фото продуктов |
| `/api/analyze` | да, `photo` | распознавание фото (роут без вызывающих, проверка стоит для полноты правила) |
| `/api/search-recipe` | да, `text` | новый текстовый запрос |
| `/api/photo-recipe` (пересчёт по чипам) | нет | те же продукты, это regenerate другими словами |
| `search-recipe` с `requestVariant` | нет | тот же запрос, «другой рецепт» |
| `search-recipe` с `cacheOnly` | нет | демо-чипы Главной, OpenAI не вызывается |
| `/api/recipe`, `/api/regenerate` | нет | другое блюдо из уже подобранной тройки |
| `/api/ask`, `/api/daily` | нет | вопрос по открытому рецепту, рецепт дня |
| «Идеи», список покупок, банкеты, админские черновики | нет | ИИ там есть, подбора нет |

Логика в `lib/podbor.ts`. **Это НЕ замена общему лимиту:**
`checkAndConsumeAiRateLimit` (10/час, 30/сутки) остаётся для всех, включая
Премиум, и не ослабляется. Два разных предохранителя: тот защищает расходы на
OpenAI, этот продаёт Премиум.

Неделя — с понедельника 00:00 по Москве (`lib/premiumPeriod.ts`). Сроки при
покупке **складываются**: новый конец = `max(сейчас, текущий конец) + срок`.

### Роуты

`/api/premium/status` (POST — состояние и остаток подборов; **POST, а не GET:
session_id гостя это фактический токен владения, в query-строке он утёк бы в
логи прокси и Referer**), `/api/premium/checkout`, `/api/premium/order`,
`/api/premium/history`, `/api/premium/robokassa/result`,
`/api/admin/premium/{payments,users,grant,settings}`.

**`/api/premium/robokassa/result` — единственное место, где выдаётся Премиум.**
`isTrustedOrigin` там НЕ применяется сознательно: роут зовёт сервер Robokassa, у
которого нашего Origin нет и быть не может. Защита — подпись Паролем #2.
Идемпотентность сделана атомарным захватом заказа (`update … where status =
'pending'`), а не «сначала срок, потом статус»: два одновременных повтора
Robokassa иначе дали бы два срока за один платёж.

`/premium/success` **ничего не выдаёт** — только опрашивает статус заказа.
Иначе платный срок выдавался бы по адресу, который человек может набрать сам.

Ключи Robokassa — только в env (`lib/robokassaConfig.ts`): нет ключей →
checkout отвечает 503 «Оплата заработает в ближайшие дни», а не 500.

### Правило iOS (App Store 3.1.1) — ЖЁСТКО

В среде `native-ios` (`lib/installEnv.ts`) не должно быть **ни цен, ни кнопок
оплаты, ни ссылок на них**. Одно условие на всё — `isPaymentUiBlocked()` в
`lib/premiumIos.ts`, есть тест. Проверяется **только среда**: прятать что-то от
проверяющих Apple по гео, дате или аккаунту нельзя.

Что это значит на практике:
* ссылок на `/premium` и `/oferta` нет нигде (подвал, профиль, шторка);
* сами `/premium` и `/oferta`, открытые в приложении, уводят на Главную;
* шторка при исчерпании лимита — нейтральная: «Подборы на эту неделю
  закончились. Новые — в понедельник» + «Понятно». Без слова «Премиум»;
* купленный на сайте Премиум работает, в профиле видно «Премиум до …», но
  кнопок «Продлить» и «Оформить» нет;
* счётчик «осталось N подборов» показывать **можно** — это не призыв к оплате.

`"unknown"` (сервер и кадр гидрации) считается РАЗРЕШЁННЫМ: иначе `/premium` не
попала бы в HTML первого ответа, а её открывает робот Robokassa и поисковик.
Платим одним кадром до гидрации.

## История инцидентов (чтобы не повторять)

1. **Утечка списка пользователей** — эндпоинт отдавал user_id + игровые поля всех пользователей без проверки прав. Закрыто.
2. **Массовая перезапись recipes.title** — на таблице recipes (и feed_posts, photo_likes, photo_comments, comment_likes, recipe_likes, party_messages, daily_recipes) не был включён RLS. Любой с публичным anon-ключом мог через прямой REST переписать/вставить записи в обход приложения. Из 1517 строк истории 1516 оказались мусором от атак. Закрыто SQL-миграцией RLS + владельческими проверками в коде + очисткой.

3. **Инцидент №2 был закрыт не до конца — выяснилось 19.09.2026.** Миграция тогда добавила правильные политики, но не убрала старые широкие, созданные через дашборд, а дропала только те, что знала по имени. В итоге полтора месяца в проде жили три дыры, которых не видно в коде:
   - `recipes.session_id` (фактический токен владения) отдавался публичным SELECT — один запрос с анон-ключом из бандла выдавал список всех гостевых идентификаторов устройств;
   - `Insert own recipes` соседствовала с широкой INSERT-политикой: anon мог писать строки в чужую историю рецептов;
   - `Enable update access for all users` (PERMISSIVE, `{public}`) позволяла **любому зарегистрировавшемуся переписать чужой рецепт и присвоить его себе** — по последовательному id, без знания session_id. Ограничитель рядом покрывал только `{anon}`.

   Закрыто PR #135–#137 и #139. Найдено не чтением кода, а прогоном запросов к боевой базе.

**Общий корень всех трёх инцидентов:** отсутствие проверки владельца на уровне БД (RLS) и/или эндпоинта, а в третьем случае — ещё и расхождение между тем, что написано в миграциях, и тем, что фактически лежит в базе. Правила 1–3.2 выше — прямая защита от повторения.
