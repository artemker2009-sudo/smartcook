# CLAUDE.md — правила проекта SmartCook

## ⛔ Правила безопасности (обязательны ВСЕГДА)

Сверяйся с этим разделом перед **каждой** правкой бэкенда или базы данных.

### 1. RLS обязателен на каждой таблице с пользовательскими данными

У нас Supabase, и anon-ключ публично доступен в браузере — любой может делать запросы к API от имени анонимного клиента. Поэтому:

- **Каждая** таблица с пользовательскими данными обязана иметь включённый Row Level Security (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
- Каждая política обязана проверять владельца записи, например:

```sql
CREATE POLICY "users_select_own"
ON public.recipes
FOR SELECT
USING (auth.uid()::text = session_id);
```

- **Запрещено** писать `USING (true)` (или `WITH CHECK (true)`) без проверки владельца. Если данные действительно публичные для всех — это должно быть явное осознанное решение, зафиксированное комментарием в миграции, а не значение по умолчанию.
- Отдельные политики нужны для каждой операции: SELECT, INSERT, UPDATE, DELETE. Для INSERT/UPDATE обязателен `WITH CHECK` с проверкой владельца.
- Помни про типы колонок: если владелец хранится как text (session_id), сравнивай `auth.uid()::text = session_id`; если как uuid (user_id) — `auth.uid() = user_id` без каста.

### 2. Каждый эндпоинт проверяет владение данными

Любой новый эндпоинт (API-роут, edge function, RPC), который читает или пишет данные пользователя:

- Проверяет аутентификацию пользователя (реальный JWT для залогиненных).
- Гарантирует, что пользователь работает **только со своими записями** — фильтрация по владельцу из проверенной сессии, а не из параметров запроса.
- Никогда не доверяет user_id/session_id, переданному клиентом в body/query как единственному доказательству владения.
- Не отдаёт в ответе лишние поля (помним инцидент: /api/feed отдавал session_id всех рецептов — это фактически токен доступа).
- Пробрасывает Authorization-заголовок в Supabase-клиент (createRequestScopedClient), иначе RLS увидит anon и сломает легитимные сценарии залогиненных.

### 3. Новая таблица = RLS-политика в той же миграции

При создании любой новой таблицы:

- В **той же миграции** сразу: `ENABLE ROW LEVEL SECURITY` + все нужные политики.
- Миграция без RLS-политик для новой таблицы с пользовательскими данными считается неполной.
- Чек перед коммитом миграции: RLS включён? Политики покрывают SELECT/INSERT/UPDATE/DELETE? Нигде нет `USING (true)` без проверки владельца?

### 4. Секретные ключи — только на сервере

- `service_role`-ключ Supabase, ключи OpenAI и любые другие секреты хранятся **только** в переменных окружения на сервере.
- **Никогда** не попадают в клиентский код, бандл, публичные репозитории или логи.
- В браузер может попадать только публичный anon-ключ.
- `.env` и аналогичные файлы обязаны быть в `.gitignore`. Перед каждым коммитом проверять, что секретов нет в staged.

### 5. Валидация и санитизация пользовательского ввода

- Санитизировать текстовые поля перед вставкой в БД (обрезка длины, удаление управляющих символов).
- Ограничивать размер загружаемых фото и длину текстовых запросов до вызова OpenAI (защита от раздувания расходов).
- Помнить: OpenAI послушно вернёт любое название блюда — контент-фильтр это отдельная задача, не access control.

## Чек-лист перед любой правкой бэкенда / БД

- [ ] Новые/изменённые таблицы: RLS включён, политики с проверкой владельца написаны в той же миграции.
- [ ] Нет `USING (true)` / `WITH CHECK (true)` без осознанного обоснования.
- [ ] Эндпоинты берут владельца из проверенной сессии/JWT, а не из параметров клиента.
- [ ] Ответы API не содержат чужих записей и лишних полей (особенно session_id).
- [ ] Секреты не попали в клиентский код, коммиты и логи.
- [ ] Изменения под git, есть возможность отката.

1. **Утечка списка пользователей** — эндпоинт отдавал user_id + игровые поля всех пользователей без проверки прав. Закрыто.
2. **Массовая перезапись recipes.title** — на таблице recipes (и feed_posts, photo_likes, photo_comments, comment_likes, recipe_likes, party_messages, daily_recipes) не был включён RLS. Любой с публичным anon-ключом мог через прямой REST переписать/вставить записи в обход приложения. Из 1517 строк истории 1516 оказались мусором от атак. Закрыто SQL-миграцией RLS + владельческими проверками в коде + очисткой.

**Общий корень обоих инцидентов:** отсутствие проверки владельца на уровне БД (RLS) и/или эндпоинта. Правила 1–3 выше — прямая защита от повторения.
