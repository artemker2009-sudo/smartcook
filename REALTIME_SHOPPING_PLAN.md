## 2. Архитектура

### 2.1 RLS

Три таблицы, RLS включён, **политик ноль**. Читает и пишет только `service_role`
из Route Handlers. Проверка прав — в коде:

```
member_ref из тела → select 1 from shared_list_members
                     where shared_list_id = $1 and member_ref = $2 and left_at is null
нет строки → 403, ни байта данных наружу
владелец (переименовать/архивировать) → дополнительно shared_lists.owner_ref = member_ref
```

Это строго сильнее любой membership-политики и заметно строже party-модели, где
curl с публичным anon-ключом сегодня свободно читает гостей и меню банкета.

**Проверено на живой Postgres 16 (31.08)**, не на словах: при существующей строке
в таблице роль без `bypassrls` видит `0` строк, `INSERT` от неё падает с
`42501`, а `service_role` видит данные. Подробности — в §6.

### 2.2 Реалтайм через Broadcast

После каждой успешной записи роут (на сервис-роли) шлёт `broadcast` события
`changed` в канал `shared-list:<listId>` — лёгкий пейлоад
`{type: "items"|"members", updatedAt}`, **без самих данных**. Клиенты подписаны
на канал anon-ключом ровно как `ClientRoom.tsx`. Получив `changed`, клиент
дёргает `GET` и получает свежий снимок.

Почему так:
- `postgres_changes` физически не долетит — RLS не пускает anon к WAL-событиям;
- Broadcast не завязан на `ALTER PUBLICATION` и на RLS, значит новым таблицам
  **не нужен рубильник в Dashboard** — только код;
- сервер остаётся единственным источником истины: конфликт «двое чиркнули один
  пункт» решается последней записью в БД, а не мержем на клиенте.

Плата — лишний round-trip на изменение. Для списка продуктов это приемлемо.

**Пинг шлётся по HTTP, а не через канал supabase-js.** Первая реализация
поднимала канал, ждала `SUBSCRIBED` и только потом слала `send()`. На замере это
стоило 2.8–6 секунд на КАЖДУЮ запись — рукопожатие WebSocket целиком попадало
внутрь запроса, а на Vercel было бы ещё хуже: каждый вызов роута это новая
лямбда, переиспользовать соединение нечего. У Realtime есть HTTP-эндпоинт
`/realtime/v1/api/broadcast` ровно для этого случая: один POST с сервис-ролью,
без сокета и без состояния. Пинг при этом именно `await`-ится, а не
`void`-ится: в serverless «отпущенное» обещание может быть убито сразу после
ответа, и участники не получили бы уведомления.

### 2.3 Ссылка-приглашение

`smart-cook.pro/shopping/join/<uuid>`, где `<uuid>` — `shared_lists.id`. 122 бита
энтропии UUIDv4 не перебираются, та же модель, что `/party/<uuid>`. Отдельного
`join_token` в v1 нет (решение 3).

### 2.4 Сосуществование с локальными списками

Локальные списки не трогаются **ни одной строкой** — ни формат, ни ключ
`smartcook_shopping_lists_v2`, ни `lib/shoppingList.ts`, ни `lib/shoppingLists.ts`.
Общий список — отдельная параллельная сущность:

- Новая секция «Семейные списки» в хабе, **рядом** с обычными карточками.
- Пункт «Сделать общим» в существующем нижнем листе меню списка. По нажатию
  копирует текущие позиции как стартовый набор на сервер и открывает экран
  приглашения. **Локальный список не удаляется и не меняется.**
- Указатель на «мои общие списки» — `smartcook_shared_shopping_lists_v1`:
  `[{id, name, memberRef, role}]`, без содержимого. Личность участника —
  `smartcook_shared_member_<listId>` = `{memberRef, name}`.

Про «бережную миграцию»: локальные списки человека не теряются и не заводятся
заново — его существующий список становится содержимым общего в момент, когда он
**сам** нажал «Сделать общим». Автоматически заливать все локальные списки на
сервер мы не делаем: это отправило бы приватные списки в БД без спроса, а у
гостя нет аккаунта, к которому их привязать.

## 3. Схема БД

Файл: [supabase_shared_shopping_lists.sql](supabase_shared_shopping_lists.sql).
Прогоняется руками в SQL Editor **до** мержа кода.

```
shared_lists
  id          uuid pk default gen_random_uuid()  -- он же токен ссылки
  name        text not null                       -- ≤60
  owner_ref   text not null                       -- member_ref создателя
  created_at  timestamptz not null default now()
  updated_at  timestamptz not null default now()
  archived_at timestamptz                         -- «удалён» = скрыт

shared_list_members
  id             uuid pk
  shared_list_id uuid not null references shared_lists(id) on delete cascade
  member_ref     text not null                    -- client-generated uuid
  member_name    text not null                    -- ≤50
  joined_at      timestamptz not null default now()
  left_at        timestamptz                      -- вышел, строка остаётся
  unique (shared_list_id, member_ref)

shared_list_items
  id             uuid pk
  shared_list_id uuid not null references shared_lists(id) on delete cascade
  name           text not null                    -- ≤50
  checked        boolean not null default false
  checked_by     text                             -- member_ref
  created_by     text                             -- member_ref
  created_at     timestamptz not null default now()
  updated_at     timestamptz not null default now()
  deleted_at     timestamptz                      -- мягкое удаление
```

Сверх схемы в файле миграции есть:
- **добивка колонок** `add column if not exists` — если черновик от 06.08 уже
  прогонялся, файл дополнит таблицы, не тронув данные;
- **CHECK на длины** (50/60/64) как вторая линия обороны на случай, если новый
  роут забудут пропустить через санитайз;
- **частичный индекс** `where deleted_at is null` — мягко удалённые строки
  копятся навсегда, в рабочий индекс они попадать не должны;
- **блок, снимающий все политики** с этих трёх таблиц — повторный прогон
  возвращает заявленную гарантию, а не оставляет щель после экспериментов в
  Dashboard;
- **самопроверка** — файл в конце сам печатает три строки с `rls_enabled` и
  числом политик;
- **curl-приёмка** в комментариях.

`updated_at` проставляет роут при записи — триггера нет намеренно, писатель
единственный. Лимит 60 позиций на список проверяется в коде роута, а не
триггером: запись идёт единственным путём через сервер, гонки конкурентных
вставок напрямую в БД (из-за которой в банкетах понадобился триггер) здесь нет.

## 4. Серверные роуты (Этап 3)

Все — Route Handlers на `createServiceRoleClient()`, все с `isTrustedOrigin`.

| Роут | Метод | Действие |
|---|---|---|
| `/api/shopping/shared` | POST | создать список (имя + стартовые позиции + владелец) |
| `/api/shopping/shared/[id]` | GET | без `memberRef` — превью `{name, itemCount}`; с валидным — полный снимок |
| `/api/shopping/shared/[id]/join` | POST | вступить (имя → `memberRef`) |
| `/api/shopping/shared/[id]/items` | POST | добавить позиции |
| `/api/shopping/shared/[id]/items/[itemId]` | PATCH | чиркнуть / вернуть / мягко удалить (`deleted_at`) |

Везде explicit columns — `select("id,name,checked,created_by,updated_at")`,
никаких `select("*")`. Каждый мутирующий роут после успешной записи обновляет
`shared_lists.updated_at` и шлёт broadcast `changed`.

Санитизация — переиспользуем `sanitizeShoppingName` / `sanitizeListName` /
`MAX_SHOPPING_ITEMS` / `MAX_SHOPPING_ITEM_LENGTH`, константы не дублируем.

### 4.1 Лимиты (защита от спама)

Всё на сервере, клиенту не верим. Таблица та же `ai_rate_limit_events` — своей
миграции лимитерам не нужно.

| Ограничение | Значение |
|---|---|
| Позиций в списке | 60 (`MAX_SHOPPING_ITEMS`), проверка перед INSERT |
| Длина позиции | 50, `sanitizeShoppingName` + дедуп + CHECK в БД |
| Участников в списке | 20 |
| Записи (add/check/delete) | `shopping-shared:` — 60/час, 300/день по IP **и** по `memberRef` |
| Создание списков | `shopping-shared-create:` — 5/день по IP |
| Вступления | `shopping-shared-join:` — 20/час по IP |

Отдельные префиксы — чтобы бюджет не делился с сортировкой и фото (тот же
принцип, по которому `shopping-photo` получил свой).

### 4.2 Известная ловушка для Этапа 3: обрезка по UTF-16

`sanitizeShoppingName` режет строку через `.slice(0, 50)`, то есть по UTF-16
code units. Если 50-й юнит окажется первой половиной суррогатной пары (эмодзи в
позиции 50), на выходе будет одинокий суррогат. В localStorage это безобидно и
живёт так сегодня, но **Postgres такую байт-последовательность отвергнет**, и
роут отдаст 500 вместо добавления позиции.

Лечится на Этапе 3 в серверной обёртке: резать через `Array.from(str).slice(0, 50).join("")`
либо снимать одинокие суррогаты регуляркой перед вставкой.
`lib/shoppingList.ts` при этом не трогаем — правка только на серверной стороне.
